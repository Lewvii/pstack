# 先分离，再串行化共享状态

当并发执行者可能共享可变状态时，先问它们是否真的需要同一个可变对象。不需要，就消除共享。共享确实存在时，用结构强制串行：锁文件、顺序阶段、独占所有权。说明和约定不是并发控制。

**为什么：** 对共享状态的并发写入会产生竞态，这类问题间歇出现、难以复现、调试成本极高。

**模式：**
1. **识别共享的可变状态**（双方都读写的文件、双方都推送的分支、双方都定义并消费的 API）。
2. **默认做法：消除共享的写入目标。** 自问：这些执行者需要一个权威对象，还是在发布各自独立的事实？给每个执行者自己的文件、键、分支或状态目录，只在读取与汇报的边界处合并。两个 worker 把各自的 `lastX` 字段写进同一个 `state.json`，仍然是共享可变状态；`indexer-state.json` + `metrics-state.json` 则不是。
3. **只有当单一共享写入目标确实是真正的不变量时，才在结构上串行化访问**（锁文件、顺序阶段、单写入者 actor，或原子 compare-and-swap）。把“我们需要加锁”当作需要核查的设计异味，而不是默认答案。
