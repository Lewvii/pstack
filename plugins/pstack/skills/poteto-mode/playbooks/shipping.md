### Shipping

Resolve the driver skill through [poteto-mode's Non-negotiables](../SKILL.md#non-negotiables).

通过 [poteto-mode 的 Non-negotiables](../SKILL.md#non-negotiables) 解析出 driver 技能。

**落地什么由你负责。独立验证每个 PR，只从根节点落地那段连续验证通过的链，然后别再碰这个栈。** 落地需要用户的落地授权，且每次落地都要在开始下一次之前得到确认。

1. **解析出 forge，然后在落地前独立验证每个 PR。** 默认用 GitHub CLI（`gh`）。如果 `command -v origin` 成功且 Origin 能解析该仓库，那么所有 PR 操作都用 `origin pr`。否则留在 `gh` 并记录这次降级。绝不要求 Graphite（`gt`）。自下而上捕获受影响的链，记录每个 head 分支和 SHA、base 分支和 SHA、以及预期的目标仓库和分支，未涉及的 PR 不要动。在合并、上膛、rebase 或 retarget 之前，先读 [合并与重排安全](../references/merge-safety.md)。进入时检查已在排队的合并请求，对缺少第 4 步验证闸门的，在开始冗长审查之前取消并读回结果。每个 PR 一个验证者，各自是在自己 worktree 里的 subagent，通过 driver 技能像用户那样运行改动，父对 head 对比，并在该 PR 上贴出 `PASS`、`PASS+NOTES` 或 `FAIL`。只有没写这段代码的 agent 给出的结论才算数，因为作者检查的是自己本来想做什么。CI 变绿和机器人审查通过都不是结论，因为两者都不会像用户那样运行改动。记录每个结论的 head SHA、base SHA、base 分支，以及 base 到 head 的 diff 的稳定 `git patch-id`。
2. **只落地以底部为根的连续验证段。** 从最低的未合并 PR 往上走，在第一个没有 `PASS` 或 `PASS+NOTES` 的 PR 处停下。它下面的那些 PR 就是这一段，最上面那个是天花板。位于未验证 PR 之上的已验证 PR 要等，因为离开下面的代码它无法落地。某个 PR 的分支既不包含也不需要那段代码时，它可以挪到 trunk 上单独落地。它需要新的结论，因为旧结论是在那段代码位于其下时跑出来的，而 trunk 上没有那段代码。
3. **重新核对结论是否仍然描述这份代码。** 结论覆盖的是一个 patch，而链上的 rebase 会把上面的每个 PR 移到新 SHA，却不使任何检查失败。在信任较旧的结论之前，比较结论所在 SHA 与当前 head 的 `git patch-id`。当 patch 只在测试、文档或 lint 配置上有差异时，只要该 lane 所运行的内容在两个 SHA 上构建结果相同（除去噪音），它的结果依然成立。噪音是指在结论 SHA 的两次构建之间也会出现的差异，或内嵌的提交 SHA。连同文件一起报告每一类噪音，让读者能自己核对这个判断。改动本身仍要重新检查并重新审查，因为旧结论从未见过它。像开发服务器这种没有构建输出的 lane 无法体现这一点，所以重跑它，并对其他发生漂移的部分重新验证。patch-id 一致只在你确认它适用于新的目标和依赖之后，才能保留原有审查，所以对行为变化或适用性存疑的部分重新验证，并在每次重写或 retarget 之后重跑检查与可合并性。
4. **自下而上，一次落地一个 PR。** 始终在服务端强制执行 head 条件的前提下合并这一段里最低的未合并 PR，因为最后时刻的无保护读取会留下竞态。在 GitHub 上用 `gh pr merge <pr> --repo <owner/repo> --squash --match-head-commit <verified-head>`，并在发出请求前立刻确认目标，因为这个 head 守护并不保护 base。只有当 Origin 的 CLI 能证明存在等价的服务器端 head 条件时，才使用 `origin pr merge <pr>`。否则停在 merge-ready 并报告这一限制。在 Origin 上，这条不带附加参数的命令还会合并你所指定 PR 之下的每一个 PR；在 GitHub 上，base 仍是其父分支的 PR 会合并进那个分支，而不是 trunk。读回该 PR 确认结果（`origin pr view <pr>` 或 `gh pr view <pr> --json state,mergedAt,baseRefName`），因为合并命令在合并队列只是把 PR 排了队时也会报告成功，而请求的自动合并并不等于已合并。已落地的 PR 读出来是 merged 且 base 为 trunk，而不是它的父分支。然后 fetch 目标分支，确认合并提交在其历史中；有任何与已验证落地相矛盾之处就停下整条链。只有在结论覆盖其当前 head 的 PR 上才上膛 `--auto`（Origin 的 merge-when-ready 或 GitHub 的 auto-merge），因为它会落地当时就绪的任意 head；并且只有在仓库规则对将要落地的那个修订强制执行结论和必需 CI 时才这么做。要求使用队列的分支会把普通合并变成入队，所以它同样受这些规则约束。绝不为了达到目的而修改保护设置或使用 `--admin`。在任何 push、rebase 或修改 base 之前，对这次改动可能影响的每个 PR 运行安全参考中的 `ship-pr inspect` 和 `ship-pr cancel-pending`，并要求结果为 `cancelled`。如果取消失败、状态不可得，或期间有 PR 合并了，先停下来核对真实状态。一次合并落地后，把 base 为被合并分支的那个 PR retarget 到 trunk（`origin pr edit <pr> --base <trunk>` 或 `gh pr edit <pr> --base <trunk>`），按记录中的旧父边界只把它自己的提交重放到合并结果上（如安全参考所述），并用一个针对重写前捕获的远端 SHA 的 lease 推送。结论覆盖的是 patch 而不是提交，所以由第 3 步的 patch-id 规则判定该结论是否依然有效。检查通过且结论依然有效后合并它。
5. **落地期间别碰这个栈。** 第 4 步里移动下一个 PR 是对分支或 base 的唯一改动，因为一次合并落地的是那一刻其分支和 base 的内容，无论有没有结论。在 GitHub 上，用 `playbooks/babysit.md` 里的 queued watcher（`scripts/watch-pr/watch-pr --queued-stack --stack-prs <bottom-to-top>`）在动态模式下经 `/loop` 监视这次运行，直到它在天花板处报告 `COMPLETE`。在 Origin 上，每次 `origin pr checks <pr> --watch` 返回时，用 `origin pr view <pr> --checks` 重新读取当前 PR，直到天花板读作 merged。父分支合并时 base 移到 trunk 是预期行为，不是需要修复的损坏。合并卡住时，先弄清原因再动任何东西。每次唤醒时，通过 `ship-pr inspect` 把落地修订（包含 base OID）与已批准的记录对比，并取消证据已不适用的待处理请求。

   watcher 负责 GitHub 上的阻塞分类。保留 `BLOCKER` 原因，并经由 `playbooks/babysit.md` 路由：冲突和 `behind-base` 交给拓扑负责人，讨论串和 CI 交给 PR 负责人，人工审批闸门转为等待。对没有变化的阻塞不要重新上膛。`WAITING`（包括 `merge-queue`）不是终态。检查待定既不是失败也不是完成。诊断 `TIMEOUT` 和 `status-query` 类阻塞，因为状态未知时永远不允许合并。
6. **停在天花板处。** 延长这一段需要新的结论，所以那是对第 1 步的一轮新循环。

**回复：** 已验证的那一段及其天花板、每个 PR 的结论和给出者、上膛或取消了什么以及读回结果、落地了什么以及你如何确认、任何未解决的状态或服务限制、以及下一个空缺需要什么。
