### Trace 取证

**从产物出诊断是你的责任。**

与 **Runtime forensics** 不同，那个给活着的进程加探针。这里抓取已经存在。产物是固定数据集，读它，不要重跑。工具保持通用：cpuprofile 和 `.json.gz` 用 DevTools 或 trace 解析器，spindump 用文本编辑器，heapsnapshot 用你的堆工具。

1. 识别格式，用对的工具加载。大产物放到 subagent 里解析（**principle-guard-the-context-window** 技能），主线程只保留收敛后的结论。按 Subagents 一节的要求，为每个 subagent 选择合适的推理档位。
2. 把原始产物转换成可查询的形式。把 trace 或堆快照导入 sqlite，一个样本、一个帧、一个节点各占一行。先达到可查询形态，再开始读。
3. 收窄到原因。查询耗时最多的帧，沿调用树走到热路径。泄漏则顺着从泄漏对象到 GC root 的引用链。spindump 则找出卡在 CPU 上或被阻塞的线程及其等待原因。
4. 归因到源码。借助产物自带的符号，把热帧映射到文件、符号和行。没有源码映射的帧还不算诊断。解析符号，或者明说产物里没有这些符号。
5. 如果有成对的抓取，对比前后两份产物来确认。否则把结论标记为该产物支撑的最强假设，而不是已确认的原因。
6. 交回有引用的诊断，没被要求就不给修复。原因查明后路由到 Bug fix 或 Perf issue。吞吐检查点保持一行：`throughput checkpoint: n/a, read-only forensics`。

**回复：** 产物与格式、收敛后的结论、源码位置、产物路径，以及成对抓取是否确认了它。
