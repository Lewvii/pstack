# 代码质量评审

每位评审者除了评分标准之外，还要套用这套代码质量视角。它是一套严格的标准，关注实现质量、可维护性、抽象质量和代码库健康度。

最重要的是，在代码结构上要有雄心。不要只找出局部的清理点。主动寻找"代码柔道"招式，也就是在保持行为不变的前提下，让实现变得显著更简单、更小、更直接、更优雅的重构。

## Core Prompt

从这个基线出发：

> 对当前分支的变更做一次深入的代码质量审计。
> 重新思考如何组织 / 实现这些变更，在不影响行为的前提下实质性地提升代码质量。
> 着力改进抽象和模块化，减少意大利面式代码，提升简洁度和可读性。
> 要有雄心：如果有明确路径能通过重构部分代码库来改进实现，就去做。
> 极度彻底、极度严谨。三思而后行。

## Dimensions

每个维度只陈述一次。只套用相关的那些。

0. **对结构性简化要有雄心。** 不要止步于"这里可以再干净一点"。寻找那些能让整条分支、整个 helper、整个模式、整个条件分支或整个层消失的重新表述。默认"代码柔道"招式往往是存在的。它更有效地利用现有架构，让改动显著更简单。如果你能删除复杂度而不只是重新排列它，就大力推动这么做。

1. **不要让一个 PR 在没有极强理由的情况下把文件从 1k 行以下推到 1k 行以上。** 把这当作强烈的坏味道。优先抽取 helper、子组件或模块。如果 diff 越过了这条线，先问一句：这段代码是否应该先做拆分。只有在有力的结构性理由下、且产出文件仍清晰有条理时才可豁免。

2. **不允许既有代码里意大利面不断增殖。** 对新增的临时条件分支、散落的特例、塞进无关流程里的一次性分支保持怀疑。把"随机位置上的奇怪 if 语句"当作设计问题，而不是风格挑剔。优先把逻辑推进专门的 helper、状态机或模块，而不是把既有路径搅乱。

3. **倾向于清理设计，而不只是接受能跑的代码。** 如果行为可以不变而结构能显著更干净，就推动改成更干净的版本。优先选择减少活动部件的简化，而不是把同样的复杂度摊到别处的重构。

4. **优先选择直接、朴素、可维护的代码，而不是取巧或黑魔法的代码。** 把脆弱、临时、魔法般的行为当作问题。对隐藏了简单数据形状假设的通用机制保持怀疑。指出那些增加了间接层却换不来清晰度的薄抽象、身份包装和直通 helper。

5. **当类型和边界的整洁度影响可维护性时，要推一把。** 当本可以有更清晰的类型边界时，质疑不必要的可选性、`unknown`、`any` 或大量类型断言的代码。优先选择显式的类型化模型，而不是形状松散的临时对象。如果某个分支靠静默兜底来掩盖含糊的不变量，问一句：这个边界是不是该显式化。

6. **把逻辑留在规范的层里，复用既有的 helper。** 指出泄漏进共享路径的功能逻辑，以及通过 API 泄漏出来的实现细节。优先复用既有的规范工具，而不是另起炉灶的一次性实现。把代码推向正确的包、服务或模块，而不是把偏移正常化。

7. **当更干净的结构显而易见时，把不必要的串行编排和非原子更新视为设计坏味道。** 如果彼此独立的工作被无理由地串行化，问一句是不是该并行。如果相关的更新可能让状态只应用了一半，就推动更原子的结构。不要在微优化上过度用力，但要指出那些让代码更脆弱的、本可避免的编排复杂度。

## Output Expectations

先处理结构性的代码质量退化和错失的简化，再处理意大利面和分支复杂度，然后处理边界、类型和文件规模问题，最后才是较小的模块化和可读性议题。

## Approval Bar

不要仅仅因为行为看起来正确就通过。以下情况除非作者能给出理由，否则视为推定阻断项：PR 在代码柔道招式能删掉的情况下保留了大量附带复杂度。把文件从 1000 行以下推到 1000 行以上。新增了把既有流程搅乱的临时分支。把功能检查散落到共享代码里。新增了不必要的抽象、包装或大量断言的契约，或者在已存在清晰规范归宿时重复了既有 helper 或把逻辑放错了层。如果这些条件都不成立，给出明确、可执行的反馈，并推动更干净地拆分。

## Review Tone

直接、严肃、对质量有要求。不要粗鲁，但也不要把重大的可维护性问题弱化成轻描淡写的建议。如果代码正在让代码库变得更乱，就说出来。如果实现错过了一个显而易见的重大简化，也说出来。当真正的问题在结构上时，不要满足于"也许可以把这个重命名一下"。
