# 维护验证技能

On Codex, read the [platform mapping](../poteto-mode/references/codex-tools.md), including its per-skill notes, before following this skill.

On GitHub Copilot, read the [platform mapping](../poteto-mode/references/copilot-tools.md), including its per-skill notes, before following this skill.

应用一变，功能地图就开始腐坏。本技能是 `/create-verification-skill` 生成的技能（或任何带功能地图的项目本地验证技能）的维护循环。严谨度的单位是功能，而不是每一句话：从源码覆盖每个功能文件，实时操作每个功能，但不必把每个要点都逐条落到终端上验证。

## 结果

选一个，并说明是哪个：

- **clean**：每个功能都得到了源码和实时覆盖；没有值得交付的内容。不建分支，不开 PR。
- **changed**：一个 PR 交付已证实的文档、测试设施或地图修正。
- **blocked**：覆盖无法完成，或者一个已证实的修复无法安全交付。准确说明是什么阻碍了它。

## 编辑范围

只编辑验证技能自己的目录（它的 SKILL.md、features/，以及它拥有的任何测试设施脚本）。运行期间绝不编辑产品代码：地图描述了而应用已不再具备的行为，要么是文档漂移（修地图），要么是产品回归（报告它，不要在文档里掩盖）。

## 一轮流程

0. **定位目标。** 找到要维护的验证技能：正文含有 launch/drive 段和功能地图的那个项目本地技能（`.claude/skills/verify/`, or `.claude/skills/verify-*/` from an older generator，即旧版生成器产出的 `.claude/skills/verify-*/`）。有多个候选就问是哪一个；一个都没有就停下，引导用户使用 `/create-verification-skill`，而不是凭空造一个目标。

1. **索引整理。** 阅读功能地图的 README，并 glob 它同级的文件。修复缺失、多余、重复或失效的条目。轻量处理，不生成清单。

2. **源码波次。** 每个功能文件一个只读子代理，并发启动。每个子代理从源码解释"这个面向用户的功能是如何工作的？"，标出可能的文档漂移并附引用，返回一份简洁的实时验证方法。子代理绝不驱动应用，绝不编辑文件。返回形式：功能摘要 / 源码入口 / 可能的漂移或无 / 一份验证方法。

3. **对账。** 每个功能文件都有一份返回的摘要。把重叠的验证方法合并到尽可能少的应用状态中。抽查被引用的漂移；不要重新证明那些干净的结论。扫一遍近期的改动，找出地图中缺失的面向用户的界面：认定某项缺失之前，必须给出具体的源码路径。

4. **实时检查。** 即使源码看起来是干净的也必须做。所有驱动都由协调者负责；遵循验证技能自身的启动模型：对服务和 UI，用一个长期运行的实例串行驱动；对短生命周期的 CLI，每次驱动用一个全新的隔离会话（由技能的 Launch 段决定，而不是本技能）。每个功能至少操作一次，并在整轮中坚守三条不变式，无论出现什么失败：(1) 绝不驱动一个自上次出现意外后还没做过健康检查的实例：首次驱动前做 doctor，在以会话为单位的场景中每个新会话做 doctor，任何驱动失败后再做 doctor；当 doctor 看不到故障时（进程健康但 UI 卡死），重置到已知状态或重新启动，而不是寄希望于侥幸；(2) 迄今采集的证据在每次清理后都要保留，并在指定位置核实，而不是假定；(3) 驱动启动的任何东西都不能比该驱动的用处活得更久：无论会话是卡住、已退出还是共享的，失败迭代的残留都要清理（对于共享实例，清理残留，而不是实例本身）。由技能漂移导致的 doctor 失败就是漂移：在编辑范围内修复，并重试一次（只重启被这次修复弄失效的东西，不多做），之后再判定本轮为 `blocked`。一个无法到达的功能，只有在给出具体前置条件（认证、权限、操作系统、外部状态）和所尝试的路径时，才能标为 `verified-unreachable`；如果地图漏掉了这个前置条件，那就是漂移。分诊中产生的任何测试设施修复，在交付前都要重新实时驱动一遍。最终关闭发生在本次运行的最后一次驱动之后（包括那些重新证明），确保没有任何东西比本次运行活得更久（证据按技能规定保留）。

5. **分诊。** 用户视角的描述错误或缺失 → 文档漂移，修复它。行为正常但测试设施驱动不了 → 测试设施缺口，修复它；测试设施修复遵循与生成时相同的 helpers 规则（脚本可执行，调用方式写在技能正文中）。应用行为确实坏了 → 产品缺口；为用户记录下来，不放进这个 PR。

6. **交付或停止。** 对于 changed：一个包含已证实修正的 PR，先重新阅读每个改动过的文件。对于 clean 或 blocked：不开 PR，如实报告结果和覆盖情况。

在临时位置保留简洁的运行笔记（覆盖的功能、无法到达的前置条件、确认的漂移、结果）；不要提交它们。
